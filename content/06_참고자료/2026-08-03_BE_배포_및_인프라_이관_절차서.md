## 1. 현재 배포 구조 확인

### 1.1 배포 구성 확인

현재 백엔드는 EC2 1대에서 Docker Compose로 실행한다.

| 구성            | 역할                      |
| --------------- | ------------------------- |
| EC2             | 애플리케이션 실행 서버    |
| Nginx           | HTTP/HTTPS reverse proxy  |
| Spring Boot App | 백엔드 API 서버           |
| MySQL           | 서비스 DB                 |
| Certbot         | Let's Encrypt 인증서 발급 |
| S3              | 이미지/영상 파일 저장소   |
| DockerHub       | Docker image 저장소       |
| GitHub Actions  | 빌드/배포 자동화          |
| Google OAuth    | Google 로그인             |

운영 서버 배포 디렉토리:

```text
/opt/kx-backend
```

주요 파일:

```text
docker-compose.aws.yml
.github/workflows/deploy.yml
nginx/templates/http.conf.template
nginx/templates/https.conf.template
```

## 3. EC2 AMI 이관

### 3.1 AMI 이관 방식 확인

AMI는 기존 EC2의 디스크 이미지를 신규 AWS 계정에 공유한 뒤, 해당 이미지로 새 EC2를 생성하는 방식이다.

S3, GitHub Actions Secrets, Google OAuth, 운영용 도메인 등 계정 외부 설정은 이후 절차에서 별도로 변경한다.

### 3.2 기존 EC2에서 AMI 생성

기존 AWS 계정에서 진행한다.

1. `AWS Console > EC2 > Instances` 이동
2. 기존 운영 EC2 instance 선택
3. `Actions > Image and templates > Create image` 선택
4. AMI 이름/설명 입력
5. 가능하면 재부팅 허용 후 생성
6. `EC2 > AMIs`에서 상태가 `available`인지 확인

EBS snapshot이 암호화되어 있으면 KMS key 공유 또는 snapshot copy 권한이 추가로 필요할 수 있다.

### 3.3 신규 AWS 계정에 AMI 공유

1. `AWS Console > EC2 > AMIs` 이동
2. 생성한 AMI 선택
3. `Actions > Edit AMI permissions` 선택
4. 신규 AWS Account ID 추가
5. 저장

### 3.4 신규 계정에서 EC2 생성

신규 AWS 계정에서 진행한다.

1. `AWS Console > EC2 > AMIs > Private images` 이동
2. 공유받은 AMI 선택
3. `Launch instance from AMI` 실행
4. Key Pair, VPC, Subnet, Security Group 설정
5. EC2 생성 후 SSH 접속 확인

Security Group 권장 설정:

| Port | Source              | 용도              |
| ---- | ------------------- | ----------------- |
| 22   | 운영자 IP           | SSH               |
| 80   | `0.0.0.0/0`, `::/0` | HTTP, 인증서 발급 |
| 443  | `0.0.0.0/0`, `::/0` | HTTPS             |

`8080`, `3306`은 외부에 공개하지 않는다.

### 3.5 SSH 접속 확인

Ubuntu AMI 예시:

```bash
ssh -i company-key.pem ubuntu@<new-ec2-ip>
```

Windows PowerShell 예시:

```powershell
ssh -i "C:\keys\company-key.pem" ubuntu@<new-ec2-ip>
```

기본 사용자명:

| AMI 계열     | 기본 사용자 |
| ------------ | ----------- |
| Ubuntu       | `ubuntu`    |
| Amazon Linux | `ec2-user`  |

접속 실패 시 Security Group의 22번 포트와 private key 파일을 확인한다.

### 3.6 신규 EC2 상태 확인

```bash
cd /opt/kx-backend
docker compose -f docker-compose.aws.yml ps
```

정상 기준:

- `kx-backend`: `Up`
- `kx-nginx`: `Up`
- `kx-mysql`: `Up` 또는 `healthy`

비정상 예:

- `Exited`
- `Restarting`
- `unhealthy`

## 4. S3 데이터 이관

### 4.1 이관 대상 확인

| 항목               | 값                     |
| ------------------ | ---------------------- |
| Source Bucket      | `<source-bucket>`      |
| Source Region      | `ap-northeast-2`       |
| Destination Bucket | `<destination-bucket>` |
| Destination Region | `ap-northeast-2`       |

### 4.2 신규 S3 Bucket 생성

신규 AWS 계정에서 생성한다.

```text
AWS Console > S3 > Create bucket
```

권장 설정:

- Region: `ap-northeast-2`
- Block Public Access: 활성화
- Object Ownership: Bucket owner enforced 권장

### 4.3 기존 Bucket 읽기 권한 추가

기존 AWS 계정의 source bucket에 신규 계정 read 권한을 추가한다.

```text
AWS Console > S3 > source bucket > Permissions > Bucket policy
```

```json
{
  "Sid": "AllowDestinationAccountReadAccess",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::<destination-account-id>:root"
  },
  "Action": ["s3:ListBucket", "s3:GetObject"],
  "Resource": ["arn:aws:s3:::<source-bucket>", "arn:aws:s3:::<source-bucket>/*"]
}
```

### 4.4 이관용 IAM 권한 생성

신규 AWS 계정에서 S3 이관용 IAM user 또는 role을 생성한다.

```text
AWS Console > IAM > Users 또는 Roles
```

필요 권한:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:GetObject"],
      "Resource": [
        "arn:aws:s3:::<source-bucket>",
        "arn:aws:s3:::<source-bucket>/*"
      ]
    },
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:PutObject"],
      "Resource": [
        "arn:aws:s3:::<destination-bucket>",
        "arn:aws:s3:::<destination-bucket>/*"
      ]
    }
  ]
}
```

### 4.5 AWS CLI 준비

S3 sync는 신규 EC2 또는 AWS CLI가 설치된 관리자 PC에서 실행한다. 혼선을 줄이기 위해 신규 EC2에서 실행하는 방식을 권장한다.

설치 확인:

```bash
aws --version
```

명령을 찾을 수 없으면 AWS CLI를 먼저 설치한다.

Credential 설정:

```bash
aws configure
```

입력값:

```text
AWS Access Key ID: <migration-access-key>
AWS Secret Access Key: <migration-secret-key>
Default region name: ap-northeast-2
Default output format: json
```

### 4.6 S3 데이터 복사

```bash
aws s3 sync s3://<source-bucket> s3://<destination-bucket> \
  --source-region ap-northeast-2 \
  --region ap-northeast-2
```

정상 기준:

- 명령이 오류 없이 종료됨
- destination bucket에 object가 생성됨
- 주요 이미지/영상 파일 접근 가능

### 4.7 애플리케이션 S3 설정 변경

신규 EC2의 `.env`에 destination bucket 정보를 반영한다. 전체 변수 설명과 예시는 `7. EC2 환경변수 수정`을 참고한다.

확인할 변수:

- `STORAGE_TYPE`
- `AWS_S3_BUCKET`
- `AWS_S3_REGION`
- `AWS_ACCESS_KEY_ID`
- `AWS_SECRET_ACCESS_KEY`

EC2 IAM Role을 사용할 경우 access key 대신 instance role 권한으로 대체할 수 있다. 운영 기준으로는 EC2 IAM Role 사용을 권장한다.

## 5. 운영용 도메인 연결

### 5.1 운영용 도메인 확정

운영 API 도메인을 먼저 확정한다. 이 값은 `.env`, HTTPS 인증서, Google OAuth, fal.ai webhook에 사용한다.

예시:

```text
api.example.com
```

### 5.2 도메인에 EC2 IP 연결

도메인을 구매했거나 관리 중인 사이트의 DNS 설정 화면에서 운영용 도메인을 신규 EC2 IP로 연결한다.

일반적으로 A record를 추가하거나 수정한다.

```text
Record Type: A
Name: api
Value: <new-ec2-ip>
```

예시:

```text
api.example.com -> 13.125.xxx.xxx
```

운영 안정성을 위해 EC2 public IP 대신 Elastic IP 사용을 권장한다.

### 5.3 DNS 반영 확인

```bash
nslookup <api-domain>
```

정상 기준:

- 조회 결과에 신규 EC2 IP가 표시됨

## 6. DockerHub 설정

### 6.1 DockerHub Repository 준비

운영 DockerHub 계정 또는 조직에 backend image repository를 준비한다.

현재 GitHub Actions는 아래 형식의 image 이름을 사용한다.

```text
<DOCKERHUB_USERNAME>/kx-backend
```

예시:

```text
company/kx-backend
```

Repository가 private이면 GitHub Actions와 EC2에서 DockerHub login이 필요하다. 현재 workflow는 `DOCKERHUB_TOKEN`으로 DockerHub에 로그인한 뒤 image를 push/pull한다.

### 6.2 DockerHub Access Token 생성

운영 DockerHub 계정에서 access token을 생성한다.

```text
DockerHub > Account Settings > Security > Access Tokens
```

권장 권한:

- GitHub Actions에서 image push 필요: Read/Write 권한
- EC2에서 private image pull 필요: Read 권한

운영 편의상 하나의 token으로 push/pull을 처리할 수 있다. 보안 기준을 더 엄격히 적용하려면 push용 token과 pull용 token을 분리한다.

### 6.3 Docker Image 이름 확인

현재 workflow는 GitHub Secret `DOCKERHUB_USERNAME`을 기준으로 image 이름을 만든다.

```yaml
IMAGE_NAME: ${{ secrets.DOCKERHUB_USERNAME }}/kx-backend
```

배포 시 생성되는 tag:

```text
<DOCKERHUB_USERNAME>/kx-backend:latest
<DOCKERHUB_USERNAME>/kx-backend:<commit-sha>
```

EC2의 `DOCKER_IMAGE` 값은 일반적으로 아래처럼 설정한다.

```properties
DOCKER_IMAGE=<DOCKERHUB_USERNAME>/kx-backend:latest
```

회사 DockerHub repository를 새로 사용하는 경우 repository는 처음에는 비어 있다. GitHub Actions Secrets를 회사 DockerHub 값으로 변경한 뒤 workflow를 1회 실행하면 backend Docker image가 회사 repository에 push된다.

최초 push가 완료되어야 EC2에서 아래 image를 pull해 실행할 수 있다.

```text
<DOCKERHUB_USERNAME>/kx-backend:latest
```

최초 image push 방법:

1. GitHub repository에서 `Settings > Secrets and variables > Actions`로 이동한다.
2. `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`을 회사 DockerHub 값으로 등록한다.
3. `EC2_HOST`, `EC2_USERNAME`, `EC2_SSH_KEY`, `EC2_APP_DIR`도 신규 EC2 기준으로 등록한다.
4. GitHub repository의 `Actions` 탭으로 이동한다.
5. `Build and deploy` workflow를 선택한다.
6. `Run workflow`를 클릭해 수동 실행한다.
7. 실행이 완료되면 DockerHub repository에서 `kx-backend:latest` image가 생성되었는지 확인한다.

workflow가 실패하면 GitHub Actions 로그에서 DockerHub login, image push, EC2 SSH 접속 단계 중 어느 단계에서 실패했는지 확인한다.

### 6.4 DockerHub 값 반영 위치

| 값 | 반영 위치 | 설명 |
| --- | --- | --- |
| `DOCKERHUB_USERNAME` | GitHub Actions Secret | DockerHub 사용자명 또는 조직명 |
| `DOCKERHUB_TOKEN` | GitHub Actions Secret | DockerHub login용 access token |
| `DOCKER_IMAGE` | EC2 `.env` | EC2에서 실행할 Docker image |

현재 workflow는 EC2에 SSH 접속한 뒤 `DOCKERHUB_TOKEN`으로 `docker login`을 수행한다. 따라서 `DOCKERHUB_TOKEN`은 GitHub Actions Secrets에 등록되어 있어야 한다.

## 7. EC2 환경변수 수정

### 7.1 Secret 취급 주의

`.env`에는 DB 비밀번호, JWT Secret, API Key, AWS credential 등이 포함된다.

주의:

- `.env` 파일은 GitHub에 업로드하지 않는다.
- API Key와 비밀번호는 이메일/메신저 평문으로 공유하지 않는다.
- 화면 캡처 시 Secret 값이 보이지 않게 처리한다.
- 이관 완료 후 임시 Access Key는 폐기한다.

### 7.2 환경변수 입력 규칙

문서의 `<값>`은 실제 운영 값으로 교체한다. `< >` 문자는 입력하지 않는다.

예시:

```properties
AWS_S3_BUCKET=<destination-bucket>
```

실제 입력:

```properties
AWS_S3_BUCKET=kx-production-storage
```

값에 공백이 없다면 따옴표 없이 입력한다. 특수문자가 포함된 비밀번호나 key도 보통 따옴표 없이 입력한다. 단, 값에 공백이 들어가는 경우에는 운영 환경에서 파싱 문제가 없는지 별도로 확인한다.

### 7.3 환경변수 파일 열기

```bash
cd /opt/kx-backend
vi .env
```

### 7.4 전체 환경변수 설명

| 변수                                | 설명                                     | 입력 예시                                           | 비고                                         |
| ----------------------------------- | ---------------------------------------- | --------------------------------------------------- | -------------------------------------------- |
| `MYSQL_DATABASE`                    | MySQL DB 이름                            | `kx_backend`                                        | 기존 DB 유지 시 기존 값 사용                 |
| `MYSQL_USER`                        | MySQL 사용자명                           | `kx`                                                | 기존 DB 유지 시 기존 값 사용                 |
| `MYSQL_PASSWORD`                    | MySQL 사용자 비밀번호                    | `...`                                               | Secret                                       |
| `MYSQL_ROOT_PASSWORD`               | MySQL root 비밀번호                      | `...`                                               | Secret                                       |
| `DB_URL`                            | Spring Boot가 MySQL에 접속할 JDBC URL    | `jdbc:mysql://mysql:3306/kx_backend?...`            | Compose 내부 DB host는 `mysql`               |
| `DB_USERNAME`                       | Spring Boot DB 접속 사용자명             | `kx`                                                | 보통 `MYSQL_USER`와 동일                     |
| `DB_PASSWORD`                       | Spring Boot DB 접속 비밀번호             | `...`                                               | 보통 `MYSQL_PASSWORD`와 동일                 |
| `JWT_SECRET`                        | JWT 서명용 secret                        | 랜덤 긴 문자열                                      | Secret                                       |
| `FAL_KEY`                           | fal.ai API key                           | `...`                                               | Secret                                       |
| `FAL_WEBHOOK_URL`                   | fal.ai가 결과를 보낼 backend webhook URL | `https://api.example.com/api/generate/webhooks/fal` | API 도메인 사용                              |
| `OPENAI_API_KEY`                    | OpenAI API key                           | `...`                                               | Secret                                       |
| `GOOGLE_CLIENT_ID`                  | Google OAuth Client ID                   | `...apps.googleusercontent.com`                     | Google Cloud에서 발급                        |
| `GOOGLE_CLIENT_SECRET`              | Google OAuth Client Secret               | `...`                                               | Secret                                       |
| `DOCKER_IMAGE`                      | 실행할 Docker image                      | `company/kx-backend:latest`                         | `docker-compose.aws.yml`에서 사용            |
| `CORS_ALLOWED_ORIGINS`              | API 호출을 허용할 frontend origin        | `https://example.com`                               | 프론트 도메인                                |
| `OAUTH2_REDIRECT_URI`               | 로그인 성공 후 이동할 frontend URL       | `https://example.com/oauth/callback`                | Google callback URI와 다름                   |
| `CERTBOT_DOMAIN`                    | HTTPS 인증서 발급 대상 API 도메인        | `api.example.com`                                   | 프론트 도메인 아님                           |
| `CERTBOT_EMAIL`                     | Let's Encrypt 알림 이메일                | `admin@example.com`                                 | 만료/보안 알림 수신                          |
| `AUTH_COOKIE_SECURE`                | HTTPS 환경에서만 cookie 전송 여부        | `true`                                              | 운영 HTTPS는 `true`                          |
| `AUTH_COOKIE_SAME_SITE`             | Cookie SameSite 정책                     | `None`                                              | frontend/backend 도메인이 다르면 보통 `None` |

| `ANTHROPIC_PROMPT_CORRECTION_MODEL` | 프롬프트 보정에 사용할 Claude model      | `claude-sonnet-5`                                   | 운영에서 사용하는 모델명                     |

### 9.4 인증서 갱신 운영

Let's Encrypt 인증서는 90일 단위로 만료된다. `docker-compose.aws.yml`에는 certbot 컨테이너가 포함되어 있지만, Docker Compose 자체에는 정기 실행 스케줄 기능이 없다.

`--keep-until-expiring`은 유효한 인증서를 불필요하게 재발급하지 않는 옵션이다. 명령을 자동으로 실행해 주는 옵션은 아니므로, 인증서 갱신 명령을 별도 스케줄로 실행해야 한다.

수동 갱신:

```bash
cd /opt/kx-backend
docker compose -f docker-compose.aws.yml --profile certbot run --rm certbot
docker compose -f docker-compose.aws.yml up -d --force-recreate nginx
```

자동 갱신은 GitHub Actions schedule로 설정한다.

아래 파일을 추가한다.

```text
.github/workflows/renew-cert.yml
```

파일 내용:

```yaml
name: Renew certificate

on:
  schedule:
    - cron: "0 18 1 * *"
  workflow_dispatch:

jobs:
  renew-cert:
    runs-on: ubuntu-latest
    steps:
      - name: Renew certificate on EC2
        uses: appleboy/ssh-action@v1.2.0
        with:
          host: ${{ secrets.EC2_HOST }}
          username: ${{ secrets.EC2_USERNAME }}
          key: ${{ secrets.EC2_SSH_KEY }}
          script: |
            set -e
            cd "${{ secrets.EC2_APP_DIR }}"
            docker compose -f docker-compose.aws.yml --profile certbot run --rm certbot
            docker compose -f docker-compose.aws.yml up -d --force-recreate nginx
```

스케줄 기준:

- 위 예시는 매월 1일 18:00 UTC에 실행된다.
- 한국 시간 기준으로는 매월 2일 03:00 KST에 실행된다.
- GitHub Actions cron은 UTC 기준이다.
- `workflow_dispatch`가 포함되어 있으므로 GitHub Actions 화면에서 수동 실행도 가능하다.

## 15. 이관 진행 순서 정리

### 15.1 기존 계정 소유자 작업

기존 AWS 계정에서 먼저 처리한다.

1. 기존 EC2의 AMI 생성
2. 회사 AWS Account ID에 AMI 공유
3. 기존 S3 bucket name, region 전달

5. MySQL dump 백업 생성 및 EC2 외부 위치에 보관
6. 이관 완료 전까지 기존 EC2, S3 bucket, AMI, EBS snapshot 유지

기존 계정의 API key, access key, DockerHub token 등 개인 secret은 회사 운영 계정 기준으로 교체하는 것을 원칙으로 한다.

### 15.2 회사 담당 작업

회사 운영 계정에서 처리한다.

1. 신규 AWS 계정에서 공유받은 AMI로 EC2 생성
2. 신규 S3 bucket 생성
3. S3 이관용 IAM user 또는 role 생성
4. `aws s3 sync`로 기존 bucket 데이터를 신규 bucket으로 복사
5. 운영용 도메인을 신규 EC2 IP에 연결
6. 회사 DockerHub repository와 access token 준비
7. Google OAuth client 생성
8. OpenAI, Claude API(Anthropic), fal.ai API key 발급
9. EC2 `.env`를 회사 운영 값으로 수정
10. GitHub Actions Secrets를 회사 운영 값으로 수정
11. GitHub Actions workflow 실행
12. HTTPS 인증서 발급 및 자동 갱신 workflow 추가
13. 서비스 기능 검증

### 15.3 이관 완료 후 정리

서비스 검증 완료 후 처리한다.

- 기존 계정에 공유된 AMI 권한 제거
