## 0. 원본 대비 달라진 점

* BE 개발 담당자가 이관 절차서를 직접 작성해 전달함 — 원본 작성 시점엔 "확인 요청 중"이었던 여러 항목의 **작업 방법**이 구체화됨(실제 계정 값 자체는 여전히 미확인, 1절 하단 표 참고)
* EC2 이전 방식이 "신규 구축(재설치)"이 아니라 **AMI를 신규 계정에 공유해 그대로 복제**하는 방식으로 구체화됨(3.1절)
* S3 이전은 **신규 버킷 생성 +** **`aws s3 sync`** **+ 과도기 교차 계정 버킷 정책**으로 구체화됨(3.1절)
* SSL 인증서 자동 갱신 방안(원본 "확인되지 않음") → **신규 GitHub Actions 워크플로(`renew-cert.yml`, 매월 1회 cron) 추가로 해결** 제시됨(3.1절 주의 2)
* DB 백업 방법이 `mysqldump` 명령어 + 백업 정책(주 1회, 분기 1회 복구 테스트)까지 구체화됨(3.1절 주의 1)
* IAM 자격증명은 액세스 키보다 **EC2 IAM Role 사용을 권장**한다는 모범사례가 추가됨(4.4절)
* 환경변수 전체 목록에 **입력 예시와 반영 위치**가 함께 정리됨(4절)
* 권장 이전 절차가 11단계(원본) → BE 절차서 기준 더 세분화된 순서로 재정리됨(5절)
* **(v0.3, 2026-08-03) BE 담당자에게 6절 8건 중 2\~5번을 직접 확인받아 실제 값 반영** — EC2 `t3.small`, S3 버킷 `kx-backend-a2-storage`, Docker Hub·Google OAuth는 백엔드 개발자 개인 계정, 외부 AI API 키는 이미 회사측 발급(6절)

## 1. 요약

현재 서비스는 **정상 운영 중**이며, 프론트엔드는 Vercel, 백엔드는 AWS EC2에 배포되어 있습니다.

이전 시 가장 먼저 처리해야 할 항목은 **AWS 계정 소유권**입니다. 프로젝트 기간 중 본사 AWS 결제가 확정되지 않아 팀 개발용 개인 계정으로 EC2/S3를 운영했고, 당초 계획했던 AWS Organizations 편입이 완료되지 않은 상태로 프로젝트가 종료됐습니다. 이 계정에 서비스 데이터(MySQL, 생성 이미지·영상)가 들어 있어 이전 우선순위가 가장 높습니다.

> **도메인 현황 (2026-08-02 확인)**: 백엔드는 정식 도메인이 아니라 무료 동적 DNS인 \*\*`kx-studio.duckdns.org`\*\*를 임시로 사용하고 있습니다. 프론트엔드는 Vercel 기본 서브도메인(`kx-frontend-azure.vercel.app`)을 쓰며 커스텀 도메인은 연결되지 않았습니다. 정식 운영 전환 시 회사 소유 도메인 연결이 필요하며, 이 경우 아래 값들이 함께 바뀝니다 — FE `VITE_API_BASE_URL`, BE `CORS_ALLOWED_ORIGINS`·`OAUTH2_REDIRECT_URI`·`FAL_WEBHOOK_URL`·`CERTBOT_DOMAIN`, Google OAuth 승인된 리디렉션 URI.

| 구분                                 | 현재 소유             | 이전 필요         | 우선순위 |

## 3. 이전 대상 자산

### 3.1 AWS — 최우선

현재 팀 개발용 개인 계정에서 운영 중입니다. 아래 두 방식 중 선택이 필요합니다 — **어느 쪽을 택할지는 본사 결정 사항이며, BE 절차서는 방식 B 기준으로만 상세 절차가 정리돼 있습니다.**

**방식 A — 계정째 이관 (원본 권장안)**
기존 계정을 본사 AWS Organizations의 멤버 계정으로 편입합니다. 데이터·설정을 그대로 유지할 수 있어 다운타임이 거의 없습니다. 프로젝트 기간 중 원래 계획했던 방식입니다. *(하지만 개인 계정으로 운영 중이므로 BE 절차서에는 이 방식의 상세 절차가 없습니다.)*

**방식 B — 신규 계정에 재구축 (BE 절차서가 상세 절차를 제공하는 방식)**

* **EC2**: 기존 EC2에서 AMI(디스크 이미지) 생성 → 신규 AWS Account ID에 AMI 공유(권한 편집) → 신규 계정에서 해당 AMI로 EC2 실행. 즉 "새로 설치"가 아니라 "이미지 그대로 복제"이며, 보안그룹은 22(운영자 IP만)·80·443만 열고 `8080`·`3306`은 외부 비공개로 설정
* **S3**: 신규 계정에 새 버킷 생성 → 기존 버킷에 신규 계정 read 권한을 임시로 부여(버킷 정책) → 이관용 IAM user/role로 `aws s3 sync s3://<source> s3://<destination>` 실행 → 완료 후 `.env`의 `STORAGE_TYPE`/`AWS_S3_BUCKET`/`AWS_S3_REGION`/자격증명을 새 값으로 교체. **운영 기준으로는 액세스 키 대신 EC2 IAM Role 사용을 권장**
* **MySQL**: 자동 이관 스크립트 없음. `docker exec kx-mysql mysqldump -u kx -p kx_backend > kx_backend_backup.sql`로 덤프 → 신규 EC2의 MySQL 컨테이너에 `docker exec -i kx-mysql mysql -u kx -p kx_backend < kx_backend_backup.sql`로 복구
* **GitHub Actions Secrets**: `EC2_HOST`·`EC2_SSH_KEY` 등을 신규 EC2 기준으로 전부 교체 후 워크플로 재실행

**이전 대상 리소스**

| 리소스                | 내용                      | 비고                                                       |
| :----------------- | :---------------------- | :------------------------------------------------------- |
| EC2 인스턴스           | 백엔드 애플리케이션 + MySQL 컨테이너 | 리전 `ap-northeast-2`(서울), **인스턴스 타입** **`t3.small`**      |
| EC2 키페어            | SSH 접속용 개인키             | `deploy.yml`의 `EC2_SSH_KEY`와 동일                          |
| S3 버킷              | 생성 이미지·영상 원본            | 리전 `ap-northeast-2`, **버킷명** **`kx-backend-a2-storage`** |
| IAM 사용자·액세스 키      | S3 접근용                  | 본사 계정에서 재발급 권장, 운영은 EC2 IAM Role 권장(BE 절차서)              |
| Elastic IP / 보안 그룹 | 인바운드 80·443             | 도메인 연결 시 함께 확인. BE 절차서는 운영 안정성을 위해 **Elastic IP 사용을 권장** |

> **주의 1 — 데이터 백업 (구체화됨)**: MySQL이 EC2 내부 Docker 컨테이너로 떠 있고 데이터는 `kx_mysql_data` 볼륨에 있습니다. RDS가 아니므로 인스턴스를 종료하면 데이터가 사라집니다. BE 절차서는 `mysqldump` 명령어와 함께 **백업 주기 최소 주 1회(배포·이관 전 필수), 복구 테스트 분기 1회**를 권장 기준으로 제시합니다.
>
> **주의 2 — SSL 인증서 (해결 방안 확인됨)**: Let's Encrypt 인증서를 certbot 컨테이너로 발급하며, **compose 설정 자체에는 자동 갱신 스케줄이 없다는 점이 BE 절차서에서도 동일하게 확인됩니다.** 다만 해결 방안으로 신규 GitHub Actions 워크플로(`.github/workflows/renew-cert.yml`, 매월 1일 UTC 18:00 = KST 2일 03:00 cron + 수동 실행 가능)를 추가하는 방법이 구체적으로 제시돼 있습니다. 이 워크플로는 아직 저장소에 추가되지 않은 **예정안**입니다.
>
> **주의 3 — DB 스키마**: Flyway·Liquibase 같은 마이그레이션 도구 없이 JPA `ddl-auto: update`로 운영됩니다. 엔티티 변경이 DB에 자동 반영되는 구조라, 이전 후 스키마 관리 방식을 별도로 정하는 것이 좋습니다. *(BE 절차서에도 별도 마이그레이션 도구 언급 없음 — 원본 지적 그대로 유효)*

### 3.2 GitHub Organization

`KX-project-A2`는 2026-07-01에 생성된 org이며, 현재 소유자는 팀원 개인 계정입니다.

* 본사 계정을 Owner로 초대한 뒤 기존 소유자를 정리하는 방식이 가장 간단합니다
* 두 저장소 모두 **Public** 상태입니다. 본사 정책에 따라 Private 전환을 검토해 주세요
* 저장소의 **Actions Secrets**(아래 3.5)도 함께 넘어가므로, 이전 후 값 교체가 필요합니다

### 3.3 Docker Hub

배포 파이프라인이 Docker Hub를 경유합니다(`DOCKERHUB_USERNAME/kx-backend`). **백엔드 개발자 개인 계정으로 운영 중** — 본사 계정으로 전환하거나 AWS ECR로 이관하는 방안 검토가 필요합니다.

> **BE 절차서 보충**: 회사 DockerHub repository를 새로 쓰는 경우 처음엔 비어 있으므로, GitHub Actions Secrets를 회사 값으로 바꾼 뒤 `Build and deploy` 워크플로를 **1회 수동 실행**(`workflow_dispatch`)해야 이미지가 처음 채워집니다. 이 순서를 지키지 않으면 신규 EC2가 pull할 이미지가 없어 배포가 실패합니다.

### 3.5 GitHub Actions Secrets (백엔드)

`deploy.yml`이 참조하는 값입니다. 이전 후 전부 새 값으로 교체해야 파이프라인이 동작합니다.

| Secret               | 용도                                       |
| :------------------- | :--------------------------------------- |
| `DOCKERHUB_USERNAME` | Docker Hub 계정                            |
| `DOCKERHUB_TOKEN`    | Docker Hub 액세스 토큰                        |
| `EC2_HOST`           | 배포 대상 서버 주소(신규 EC2 public IP 또는 운영용 도메인) |
| `EC2_USERNAME`       | SSH 계정명 (Ubuntu AMI 기준 `ubuntu`)         |
| `EC2_SSH_KEY`        | SSH 개인키 전체 내용                            |
| `EC2_APP_DIR`        | 서버 내 배포 경로 (`/opt/kx-backend`)           |

> **BE 절차서 보충**: HTTPS 인증서 자동 갱신 워크플로를 추가할 경우, 위 6개 Secrets를 그대로 재사용하므로 별도 Secret 추가는 필요 없습니다.

| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`    | Google OAuth 클라이언트 | Google Cloud Console에서 발급                                    |
| `JWT_SECRET`                                   | JWT 서명 키           | 랜덤 긴 문자열                                                     |
| `OAUTH2_REDIRECT_URI`                          | 로그인 후 리다이렉트 주소     | `https://<프론트도메인>/oauth/callback` — Google callback URI와는 다름 |
| `AUTH_COOKIE_SECURE` / `AUTH_COOKIE_SAME_SITE` | 쿠키 정책              | 운영은 `true` / `None` (FE·BE 도메인이 다르면 보통 `None`)               |

> Google OAuth는 **승인된 리다이렉션 URI**가 도메인에 종속됩니다(`https://<api-domain>/login/oauth2/code/google`). 도메인이 바뀌면 Google Cloud Console에서 함께 수정해야 합니다.
> **현재 클라이언트는 백엔드 개발자 개인 계정에서 발급됨** — 본사 Google Cloud 프로젝트에서 새로 발급받는 것을 권장합니다(BE 절차서 10절 참고).

## 5. 권장 이전 절차 (BE 절차서 기준 재정리)

BE 절차서 15절("이관 진행 순서 정리")을 기준으로, 기존 계정 소유자(개발단)와 회사 담당자의 작업을 구분해 정리했습니다.

### 5.1 기존 계정 소유자(개발단) 작업 — 먼저 진행

| 순서 | 작업                                                       |
| :- | :------------------------------------------------------- |
| 1  | 기존 EC2의 AMI 생성                                           |
| 2  | 회사 AWS Account ID에 AMI 공유                                |
| 3  | 기존 S3 bucket name·region 전달                              |
| 4  | 기존 S3 bucket에 회사 AWS Account read 권한 추가(버킷 정책)           |
| 5  | MySQL dump 백업 생성 및 EC2 외부 위치에 보관                         |
| 6  | 이관 완료 전까지 기존 EC2·S3 bucket·AMI·EBS snapshot 유지(임의 삭제 금지) |

> 기존 계정의 API key·access key·DockerHub token 등 개인 secret은 회사 운영 계정 기준으로 전량 교체하는 것을 원칙으로 합니다.

### 5.2 회사 담당 작업

| 순서 | 작업                                                                           |
| :- | :--------------------------------------------------------------------------- |
| 1  | 신규 AWS 계정에서 공유받은 AMI로 EC2 생성                                                 |
| 2  | 신규 S3 bucket 생성                                                              |
| 3  | S3 이관용 IAM user 또는 role 생성                                                   |
| 4  | `aws s3 sync`로 기존 bucket 데이터를 신규 bucket으로 복사                                 |
| 5  | 운영용 도메인을 신규 EC2 IP(Elastic IP 권장)에 연결                                        |
| 6  | 회사 DockerHub repository와 access token 준비                                     |
| 7  | Google OAuth client 생성                                                       |
| 8  | OpenAI·Claude(Anthropic)·fal.ai API key 발급                                   |
| 9  | EC2 `.env`를 회사 운영 값으로 수정                                                     |
| 10 | GitHub Actions Secrets를 회사 운영 값으로 수정                                         |
| 11 | GitHub Actions workflow 실행(최초 수동 실행 필요, 3.3절 참고)                             |
| 12 | HTTPS 인증서 발급 및 자동 갱신 workflow(`renew-cert.yml`) 추가                           |
| 13 | 서비스 기능 검증(Google 로그인·이미지 업로드·생성 결과 저장·S3 object 생성·Presigned URL 다운로드·공유 링크) |

### 5.3 이관 완료 후 정리

* 기존 계정에 공유된 AMI 권한 제거
* 기존 계정에 생성된 AMI·EBS snapshot 삭제 여부 확인
* S3 이관용 버킷 정책·IAM user/access key 제거
* 기존 EC2 중지 또는 종료 여부 확인
* GitHub Actions Secrets·도메인 DNS·Google OAuth URI 최종 확인
* 신규 S3 bucket object 저장 확인, HTTPS 인증서 발급 상태 확인, API health check 정상 응답 확인

## 6. 확인이 필요한 사항 (BE 절차서 대조 결과 + BE 직접 회신 반영)

> **먼저 처리를 권장드리는 사항**: AWS가 팀원 개인 계정으로 운영되고 있어, 계정이 정리되면 EC2 인스턴스와 함께 MySQL 데이터가 사라집니다(RDS가 아닌 인스턴스 내부 컨테이너 볼륨). 이전 방식이 결정되기 전이라도 **데이터 덤프 확보와 개인 계정 정리 보류**를 먼저 요청해 두시는 것이 안전합니다. (BE 절차서에 정확한 백업 명령어가 포함되어 이 작업 자체는 바로 실행 가능합니다.)

| #  | 항목                                  | 확인 대상              | 상태                                                                          |
| :- | :---------------------------------- | :----------------- | :-------------------------------------------------------------------------- |
| 1  | AWS 이전 방식 — 계정 이관 vs 신규 구축          | 본사                 | **부분 해소** — 신규 구축(B) 방식은 절차 전체가 문서화됨. A vs B 선택 자체는 여전히 본사 결정               |
| 2  | EC2 인스턴스 사양, S3 버킷명                 | 개발단                | **해소**  — 인스턴스 `t3.small`, 버킷명 `kx-backend-a2-storage`, 리전 `ap-northeast-2` |
| 3  | Docker Hub 계정 소유자                   | 개발단                | **해소** — 백엔드 개발자 개인 계정. 회사 계정으로 전환 필요                                       |
| 4  | OpenAI·Anthropic·fal.ai API 키 발급 주체 | 본사                 | **해소** — **이미 회사측에서 발급.** 이관 시 새로 발급받을 필요 없이 현재 키를 그대로 `.env`에 반영하면 됨       |
| 5  | Google OAuth 클라이언트 발급 주체            | 개발단                | **해소** — 백엔드 개발자 개인 계정. 본사 Google Cloud 프로젝트에서 재발급 필요                       |
| 6  | 정식 도메인 연결 여부                        | 본사 (도메인 소유·DNS 권한) | **변화 없음** — 여전히 본사 결정 사항                                                    |
| 7  | 저장소 Public 유지 여부                    | 본사                 | **해당 없음** — BE 절차서 범위 밖(조직 정책)                                              |
| 8  | 이전 후 운영·유지보수 주체                     | 본사                 | **해당 없음** — BE 절차서 범위 밖(조직 문제)                                              |

**정리하면 8건 중 5건(1~5번)이 이번에 실질적으로 해소됐고, 남은 3건(6~8번)은 처음부터 본사 내부 결정 사항이라 BE 확인과 무관합니다.**

**새로 해소된 항목 (원본 3.1절 "주의" 항목 기준, 8건 리스트엔 없었으나 실질적으로 확인됨)**

| 항목               | 상태                                                                 |
| :--------------- | :----------------------------------------------------------------- |
| SSL 인증서 자동 갱신 방안 | **해소** — `renew-cert.yml` 워크플로 추가로 해결(아직 미적용 상태, 이관 작업 시 함께 추가 예정) |
| DB 백업 절차·주기      | **해소** — `mysqldump` 명령어, 주 1회 백업/분기 1회 복구 테스트 기준 확보               |
| S3 데이터 이관 구체 방법  | **해소** — 신규 버킷+`aws s3 sync`+교차 계정 정책                              |
| EC2 이관 구체 방법     | **해소** — 재설치가 아니라 AMI 공유 방식(다운타임 최소화)                              |
| IAM 자격증명 운영 방식   | **신규 권장사항 추가** — 액세스 키 대신 EC2 IAM Role                             |

**실제 이전 작업을 시작하실 때, 2·3·4·5번(실제 값이 필요한 항목)은 다시 한번 개발 담당자 회신을 요청드려야 합니다.**

## 7. 이전 전 정리 권장 사항

배포 이전과 별개로, 인수 품질을 위해 개발단에서 정리하면 좋을 항목입니다. (원본과 동일, BE 절차서에서 추가 변경 사항 없음)

* **백엔드** **`main`** **브랜치 최신화** — 현재 `dev`가 `main`보다 131커밋 앞서 있어, `main`을 클론하면 최신 코드가 아닙니다
* **백엔드 README에 배포 절차 기재** — 현재 배포 관련 설명이 없어 인수자가 파이프라인을 코드에서 역추적해야 합니다 *(BE 절차서 자체가 이 역할을 상당 부분 대신하게 됨)*
* **프론트엔드** **`civitai`** **경로 자산 정리** — 2026-07-24 회의에서 상업 사용·재배포 권리 미확인을 이유로 카탈로그에서 제외하기로 했으나, 파일 104개가 저장소에 남아 있습니다
* **`.env.example`** **보강** — BE 절차서 16절에 `.env.example` 파일이 저장소에 존재한다고 명시되어 있어, 원본이 지적했던 "예시 파일 부재" 문제는 해소된 것으로 보입니다(직접 열람은 못했으므로 내용 확인 권장)
