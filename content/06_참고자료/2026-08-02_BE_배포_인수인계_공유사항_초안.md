## 1. 현재 배포 구조 (소스코드 확인됨)

| 항목           | 내용                                                                                                                                                                                                              |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 레포           | `KX-project-A2/kx-backend` — `dev`/`main` 브랜치 푸시 시 GitHub Actions 자동 배포                                                                                                                                         |
| 배포 방식        | GitHub Actions(`.github/workflows/deploy.yml`) → Docker 이미지 빌드 → **Docker Hub**에 푸시 → EC2로 SCP 전송 → EC2에서 SSH로 `docker compose pull && up -d` 실행                                                                |
| 실행 환경        | EC2 인스턴스 1대 위에서 **nginx + Spring Boot 앱 + MySQL**이 모두 컨테이너로 함께 실행(`docker-compose.aws.yml`) — 별도 로드밸런서·컨테이너 오케스트레이션(ECS/EKS) 없이 단일 서버                                                                           |
| 현재 도메인       | `kx-studio.duckdns.org` — DuckDNS 동적 DNS(임시), FE 문서에서도 동일하게 확인됨                                                                                                                                                 |
| DB           | **AWS RDS가 아니라 EC2 위 Docker 컨테이너로 직접 띄운 MySQL 8.4** — 컨테이너 볼륨(`kx_mysql_data`)에 데이터 저장. 관리형 DB 서비스가 아님                                                                                                          |
| DB 스키마 관리    | Flyway/Liquibase 같은 버전 관리형 마이그레이션 도구 없음 — JPA `ddl-auto: update`로 엔티티 변경 시 자동 반영되는 방식                                                                                                                           |
| 이미지 저장       | **AWS S3** (담당 PM 확인 — EC2+S3 구조 맞음). 코드상으로는 로컬/S3 두 방식을 다 지원하고 `STORAGE_TYPE` 환경변수로 전환하는 구조라, 운영 서버 `.env`에 `STORAGE_TYPE=s3`+`AWS_S3_BUCKET` 등이 설정돼 있을 것으로 판단됨(값 자체는 코드에 없어 BE 확인 시 버킷명·리전만 재확인하면 됨, 2.1절 참고) |
| SSL          | Let's Encrypt(certbot) 컨테이너로 발급. `CERTBOT_DOMAIN` 환경변수에 지정된 도메인 기준으로 발급되며, 자동 갱신 스케줄(cron 등)은 compose 파일에서 확인되지 않음                                                                                              |
| Health check | `GET /api/health` 엔드포인트 존재 — 인프라 이전 시 로드밸런서/모니터링 헬스체크로 바로 활용 가능                                                                                                                                                 |
| 이미지 레지스트리    | AWS ECR이 아니라 **Docker Hub** 사용 (`${DOCKERHUB_USERNAME}/kx-backend`)                                                                                                                                             |

## 2. 정식 배포 전 확인·준비 필요한 것

### 2.1 S3 버킷 정보 확인 (BE 확인)

* 스토리지는 S3. 코드 구조상 `storage.type=s3`일 때 `AWS_S3_BUCKET`(버킷명)·`AWS_S3_REGION`(기본값 `ap-northeast-2`)·`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` 값으로 연결하도록 돼 있다(`StorageConfig.java`, `StorageProperties.java`).
* 서버 이전 시에는 이 버킷을 그대로 재사용(리전·자격증명만 새 서버에 다시 세팅)하면 되고, 이미지·영상 파일 자체를 물리적으로 옮길 필요는 없다.
* 다만 코드에는 실제 값이 없으니, 정확한 버킷명·리전과 접근 권한(IAM) 발급 방식만 BE에게 확인하면 된다.

### 2.2 MySQL이 관리형 DB로 이전됐는지

* 현재는 EC2 위 컨테이너 MySQL이라 **EC2가 죽으면 DB도 함께 죽는다.** 정식 서비스 전환 시 RDS 같은 관리형 DB로 옮길지 결정 필요.
* 백업 정책(스냅샷 등)이 현재 compose 설정에는 보이지 않는다 — 별도로 있는지 BE 확인 필요.

### 2.3 필요한 환경변수/시크릿 목록 (코드에서 이름만 확인됨, 값은 BE만 보유)

이전 시 새 서버/CI에 아래 값들을 다시 세팅해야 한다.

| 구분                         | 변수명                                                                                                                       |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| DB                         | `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` (또는 compose용 `MYSQL_DATABASE`/`MYSQL_USER`/`MYSQL_PASSWORD`/`MYSQL_ROOT_PASSWORD`) |
| 인증                         | `JWT_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `OAUTH2_REDIRECT_URI`                                           |
| AI 연동                      | `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `FAL_KEY`, `FAL_WEBHOOK_URL`                                                       |
| 스토리지(S3 사용 시)              | `AWS_S3_BUCKET`, `AWS_S3_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`                                            |
| 도메인/SSL                    | `CERTBOT_DOMAIN`, `CERTBOT_EMAIL`                                                                                         |
| 쿠키/CORS                    | `AUTH_COOKIE_SECURE`, `AUTH_COOKIE_SAME_SITE`, `CORS_ALLOWED_ORIGINS`                                                     |
| 배포(GitHub Actions Secrets) | `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`, `EC2_HOST`, `EC2_USERNAME`, `EC2_SSH_KEY`, `EC2_APP_DIR`                         |

### 2.4 Custom Domain 연결 여부 (FE와 동일한 이슈)

* 지금은 `kx-studio.duckdns.org`(DuckDNS 임시 동적 DNS) 사용 중
* 정식 도메인으로 옮기면 `CERTBOT_DOMAIN` 값 교체 + FE의 `VITE_API_BASE_URL`도 함께 교체해야 한다(FE 문서 2.2절과 연결되는 부분)

## 3. 결론

**BE 담당자와 연락 없이 저장소 코드만으로 확인 가능한 배포 구조는 위와 같이 정리했다.** 다만 아래는 코드만으로는 알 수 없어 BE 확인이 꼭 필요하다:

1. S3 버킷명·리전·IAM 접근 방식 (2.1절)
2. DB 백업이 별도로 돌고 있는지, RDS 전환 계획이 있는지 (2.2절)
3. 위 환경변수들의 실제 값 (2.3절 — BE만 보유, 절대 코드로 안 나옴)

BE 담당자 연락이 닿으면 이 세 가지부터 확인받아 문서를 최종본으로 전환하는 걸 권장한다.
