# A2팀 기능명세서 — 인수인계본 v7.0
> 작성일: 2026-07-12 | 인수인계본 정리일: 2026-08-02 | 작성자: 이슬기 (PM)
> GeNova(A2팀 생성형 AI 통합 엔진)의 기능을 화면 단위로 정리한 문서다. 실제 배포 서비스(`kx-frontend-azure.vercel.app`)를 직접 조작해 확인한 화면 구조·옵션, 개발 착수 전 설계 문서(v0.1~v0.8)의 UI 세부 사양·비동기 상태 처리 원칙·인수 조건·엣지 케이스, **백엔드 소스코드(`KX-project-A2/kx-backend`, dev 브랜치)**와 **프런트엔드 소스코드(`KX-project-A2/kx-frontend`, main 브랜치)**를 직접 읽어 확인한 실제 API 계약·화면 로직, 그리고 **실 계정으로 로그인해 역프롬프트 기능을 직접 실행한 결과**를 모두 합쳐서 썼다. 여러 출처의 내용이 서로 다를 경우 소스코드 확인 내용을 최우선으로 반영했다.

## 1. 서비스 개요

GeNova는 방송 제작자를 위한 생성형 AI 통합 편집 도구다. 한국어 프롬프트만으로 캐릭터·배경 이미지, 캐릭터 시트, 짧은 영상을 만들고, 레퍼런스 이미지에서 프롬프트를 역으로 추출할 수 있다.

| 항목 | 내용 |
|------|------|
| 화면 구조 | 단일 페이지 + 기능별 화면(좌측 사이드바로 이동) |
| 인증 | 이메일 로그인 + Google OAuth 병행 (확인됨) |
| 이미지 생성 모델 | GPT Image 2.0 — OpenAI 직접 호출 (확인됨, 2026-07-28 QA에서 fal.ai 경유 아님을 재확인) |
| 영상 생성 모델 | Seedance 2.0 / Kling 3.0 — fal.ai 경유 (확인됨) |
| 프롬프트 보조·이미지 분석 | Claude Sonnet (역프롬프트 화면에는 "Claude Sonnet 5"로 구체 버전 표기, 확인됨) |
| 스토리지 | AWS (EC2 + S3) |
| 프런트엔드 배포 | Vercel — `kx-frontend-azure.vercel.app` |
| 백엔드 배포 | AWS — `kx-studio.duckdns.org` (확인된 API 베이스 URL) |
| UI 언어 | 한국어 단일 |
| 지원 환경 | 데스크톱 웹 기준 |

## 3. 공통 동작 규칙

### 3.1 API 공통 형식

```typescript
// 성공
{ success: true, data: { ... } }

// 실패
{ success: false, error: { code: string, message: string } }
```

`error.message`는 사용자에게 그대로 보여줄 수 있는 한국어 문장이며, 프런트는 이 값을 우선 표시한다.

**프런트엔드 소스(`kx-frontend`의 `src/services/*.ts`)를 직접 읽어 전체 엔드포인트를 확인했다.** 아래가 실제 경로이며, 기존 문서(v6.0 이하)의 "설계 당시 엔드포인트(재확인 필요)" 표는 전부 틀렸던 것으로 확인되어 삭제한다.

| 엔드포인트 | 메서드 | 용도 |
|------|------|------|
| `/api/auth/email/check` | GET | 이메일 중복 확인 |
| `/api/auth/signup` | POST | 회원가입 (`{email, password, nickname}`) |
| `/api/auth/login` | POST | 로그인 |
| `/api/auth/reissue` | POST | 액세스 토큰 재발급 |
| `/api/auth/logout` | POST | 로그아웃 |
| `/api/me/profile` | GET | 내 프로필 조회 |
| `/api/generate/images` | POST (multipart: `request` JSON + `references` 파일들) | 이미지 생성(캐릭터/배경) 요청 |
| `/api/generate/images/character-concept-sheet` | POST (multipart) | **캐릭터시트 전용 생성 요청 — 7.1절 참고, 이미지 생성과 별개 엔드포인트** |
| `/api/generate/images/jobs/{jobId}` | GET | 이미지 생성 작업 상태 폴링 |
| `/api/generate/images/jobs/active` | GET | 진행 중인 이미지 생성 작업 확인 |
| `/api/generate/videos` | POST (JSON) | 영상 생성 요청 |
| `/api/generate/videos/jobs/{jobId}` | GET | 영상 생성 작업 상태 폴링 |
| `/api/generate/videos/jobs/active` | GET | 진행 중인 영상 생성 작업 확인 |
| `/api/generate/reverse-prompt` | POST (multipart: `request` JSON `{aspectRatio}` + `image` 파일) | 역프롬프트 추출 — **실행 확인됨**(9절 참고), 이미지 파일을 직접 업로드하며 사전 `mediaFileId` 불필요 |
| `/api/generate/reverse-prompt/{id}` | PATCH | 역프롬프트 결과 수정(prompt/aspectRatio) |
| `/api/generate/reverse-prompt/{id}/generate` | POST | 역프롬프트 결과로 이미지 재생성 |
| `/api/media/images/upload` | POST (multipart: `file` + `tags`) | 레퍼런스·스토리보드 이미지 업로드, mediaFileId 반환 |
| `/api/media/files` | GET (`?type=IMAGE\|VIDEO&page=&size=`) | 라이브러리 목록 조회 |
| `/api/media/files/recent` | GET (`?size=`) | 홈 화면 "탐색하기"용 최근 작업 목록 |
| `/api/media/images/{id}/download` | GET (blob) | 이미지 다운로드 |
| `/api/media/files/{id}/download-url` | GET | 영상(또는 이미지) 다운로드 URL 발급 |
| `/api/media/files/{id}` | DELETE | 라이브러리 항목 삭제 |
| `/api/media/files/{id}/favorite` | POST | 찜 추가 |
| `/api/media/files/{id}/favorite` | DELETE | 찜 해제 (찜은 PATCH 토글이 아니라 POST/DELETE 두 엔드포인트로 분리돼 있음 — 기존 문서 오류 정정) |

백엔드 `ReversePromptRequestDto.java`에는 `mediaFileId`+`aspectRatio` 필드가 있었으나, 프런트가 실제로 호출하는 추출 요청은 이미지 파일을 직접 멀티파트로 올리고 `aspectRatio`만 JSON으로 보낸다 — 두 출처가 어긋나는 지점이라, 실제 컨트롤러가 이 DTO를 그대로 쓰는지 다른 진입점을 쓰는지는 명확히 확인하지 못했다(재확인 필요, 다만 동작 자체는 실행 확인됨).

### 3.2 에러 코드 표 (백엔드 소스 확인됨 — `global.exception.ErrorCode`)

기존 문서(v5.0 이하)에 실려 있던 `INVALID_INPUT`/`AUTH_FAILED`/`SESSION_EXPIRED`/`FILE_TOO_LARGE` 등의 코드 체계는 **설계 당시 안이며 실제 백엔드에는 존재하지 않는다.** 실제 코드는 아래 14개뿐이다.

| 코드 | HTTP | 사용자 표시 메시지 | 발생 상황 |
|------|------|------|------|
| `COMMON_001` (`INVALID_INPUT_VALUE`) | 400 | "잘못된 입력값입니다." | 파라미터 검증 실패 전반 — **회원가입 유효성 오류, 업로드 파일 형식/용량 오류(10MB·jpg 초과 등 세분화 코드 없이 전부 이 코드+메시지 커스터마이즈)도 여기 포함** |
| `COMMON_002` (`UNAUTHORIZED`) | 401 | "인증이 필요합니다." | 미인증 접근 |
| `COMMON_003` (`FORBIDDEN`) | 403 | "접근 권한이 없습니다." | 권한 없는 리소스 접근 |
| `COMMON_004` (`NOT_FOUND`) | 404 | "요청한 리소스를 찾을 수 없습니다." | 존재하지 않는 리소스 |
| `COMMON_005` (`NOT_IMPLEMENTED`) | 501 | "아직 지원하지 않는 기능입니다." | 미구현 기능 |
| `COMMON_006` (`UNSUPPORTED_MEDIA_TYPE`) | 415 | "지원하지 않는 Content-Type입니다." | 잘못된 Content-Type |
| `COMMON_999` (`INTERNAL_SERVER_ERROR`) | 500 | "서버 내부 오류가 발생했습니다." | 그 외 서버 오류 |
| `AUTH_001` (`INVALID_REFRESH_TOKEN`) | 401 | "유효하지 않은 리프레시 토큰입니다." | 리프레시 토큰 위변조/불일치 |
| `AUTH_002` (`EXPIRED_REFRESH_TOKEN`) | 401 | "만료된 리프레시 토큰입니다." | 리프레시 토큰 만료 → 재로그인 필요 |
| `AUTH_003` (`DUPLICATE_EMAIL`) | 409 | "이미 사용 중인 이메일입니다." | 회원가입 이메일 중복 |
| `AUTH_004` (`INVALID_CREDENTIALS`) | 401 | "이메일 또는 비밀번호가 올바르지 않습니다." | 로그인 실패 (이메일/비밀번호 불일치 구분 없이 동일 메시지) |
| `AUTH_005` (`OAUTH_EMAIL_ALREADY_EXISTS`) | 409 | "이미 일반 회원가입으로 가입된 이메일입니다." | 로컬 계정이 이미 있는 이메일로 Google 로그인 시도 — **자동 연동되지 않고 충돌 에러 발생** (5.3절 참고, 확인되지 않은 사항이었던 항목 해소) |
| `AUTH_006` (`INVALID_OAUTH2_USER`) | 401 | "OAuth 사용자 정보를 확인할 수 없습니다." | Google 응답에 필수 속성(sub/email) 누락 |
| `GENERATE_001` (`AI_PROVIDER_ERROR`) | 502 | "AI 생성 API 호출에 실패했습니다." | 이미지·영상 생성, 역프롬프트 분석 등 AI 프로바이더(OpenAI/fal.ai/Claude) 호출 실패 — 이미지 생성 실패·영상 생성 실패·역프롬프트 분석 실패가 **전부 이 하나의 코드로 통합되어 있다.** 기존 문서의 `GENERATION_FAILED`/`VIDEO_GENERATION_FAILED`/`ANALYSIS_FAILED` 구분은 실제로 없음 |

`TIMEOUT`/`API_LIMIT_EXCEEDED`/`STORAGE_FAILED`/`UNKNOWN` 코드도 실제 백엔드에는 없다. 타임아웃이나 API 사용량 초과 상황이 발생하면 위 표의 `COMMON_999` 또는 `GENERATE_001`로 처리될 것으로 추정되나, 별도 코드로 분리돼 있지 않다는 점은 프런트 에러 메시지 분기 로직에 영향을 줄 수 있어 인수인계 시 특히 주의가 필요하다.

이번 검증에서 실제로 재현된 에러는 회원가입 1단계의 "이메일 확인에 실패했습니다. 다시 시도해주세요." 하나였다(5.1절 참고, 실제로는 503 서버 오류 — 위 14개 코드 중 어디에도 없는 응답이라, 이 503이 애플리케이션 레벨 에러가 아니라 인프라/배포 레벨 장애일 가능성을 시사한다).

### 3.3 비동기 상태 처리 원칙 (설계 당시 정의)

이미지·영상 생성처럼 시간이 걸리는 모든 비동기 동작은 아래 세 상태를 반드시 구현하도록 설계되어 있었다.

| 상태 | UI 기준 |
|------|--------|
| **Loading** | 스피너 또는 스켈레톤 + 트리거 버튼 비활성화. 2초 이상 걸리는 작업은 진행 문구 병기 |
| **Error** | 한국어 에러 메시지 + [다시 시도] 버튼. 에러 코드는 콘솔 로그로만 기록 |
| **Empty** | 안내 문구 + 해당 기능 시작 CTA 버튼 |

이미지 생성 결과 영역, 영상 생성 상태 화면, 라이브러리 그리드에서 Loading·Empty 상태는 실제로 확인됨. Error 상태 화면까지는 재현하지 못했다.

### 3.4 중복 요청 방지 규칙 (설계 당시 정의)

- 생성·저장·삭제 등 쓰기 요청은 응답 수신 전까지 트리거 버튼을 비활성화한다
- 이미지·영상 생성은 화면당 동시 1건만 허용 — 진행 중 재요청 불가
- 폴링 중 화면 이탈 시 폴링은 중단되지만, 서버 측 생성 자체는 계속 진행된다(확인됨 — 8.4절)

### 3.5 생성·저장 공통 규칙 (확인됨)

- **생성이 완료되면 사용자 조작 없이 즉시 라이브러리에 자동 저장된다.** 별도의 [저장] 버튼은 없다.
- 재생성해도 이전 결과는 삭제되지 않고 라이브러리에 별개 항목으로 남는다.
- 예외: 역프롬프트로 "프롬프트를 추출"만 한 경우는 저장되지 않는다. [이 프롬프트로 이미지 생성]로 실제 이미지를 만들었을 때 그 결과 이미지만 저장된다 (9장 참고).

### 3.6 토스트·확인 모달 규칙 (설계 당시 정의)

| 상황 | UI |
|------|----|
| 성공 피드백 (저장·복사·변경 완료) | 토스트 3초 자동 닫힘 |
| 복구 불가 동작 (삭제·탈퇴) | 확인 모달 — [취소]가 기본 포커스, 확인 버튼은 위험색 |
| 실패 피드백 | 해당 영역 인라인 에러 메시지 |

**예외(확인됨)**: 내 프로필의 회원 탈퇴는 이 규칙과 달리 커스텀 모달이 아니라 브라우저 기본 확인창(`confirm()`)으로 구현되어 있다 (11장 참고).

### 3.7 세션 만료 처리 (설계 당시 정의, 코드는 백엔드 소스 확인됨으로 정정)

어떤 API든 인증 관련 401(`COMMON_002` 미인증, 또는 리프레시 시도 시 `AUTH_001`/`AUTH_002`)을 받으면 토스트를 띄운 뒤 로그인 화면으로 이동한다. 로그인 성공 시 홈 화면으로 이동한다(만료 직전 화면 복원은 지원하지 않음). 기존 문서의 `SESSION_EXPIRED` 코드는 실제 백엔드에 없다(3.2절 참고) — `POST /api/auth/reissue`로 액세스 토큰 재발급을 시도하다 리프레시 토큰이 만료/무효면 `AUTH_001`·`AUTH_002`가 발생하는 흐름으로 추정된다(재확인 필요).

### 3.8 파일명 규칙 (다운로드, 설계 당시 정의)

| 대상 | 규칙 | 예시 |
|------|------|------|
| 이미지 | `image_{YYYYMMDD}_{HHmmss}.png` | `image_20260715_143012.png` |
| 영상 | `video_{YYYYMMDD}_{HHmmss}.mp4` | `video_20260716_101530.mp4` |

## 5. 인증 — 로그인·회원가입

### 5.1 회원가입 (AUTH-001)

**회원가입은 단일 화면 폼이 아니라 3단계 마법사다.** 실제 단계 순서는 **① 이메일 → ② 닉네임 → ③ 비밀번호**다(프런트 소스 확인됨 — `SignupEmail.tsx`→`SignupNickname.tsx`→`SignupPassword.tsx`, 라우트 `/signup`→`/signup/nickname`→`/signup/password`). 기존 문서(v6.0 이하)가 "이메일→비밀번호→닉네임"으로 추정했던 순서는 틀렸다.

**1단계 — 이메일 입력 (확인됨)**

| 항목 | 내용 |
|------|------|
| 화면 문구 | "이메일 입력" / "가입할 이메일을 입력하세요." |
| 입력 필드 | `example@kx.com` 형식 placeholder, HTML `type=email`, `required` |
| 클라이언트 제약 | `maxlength`·`minlength`·`pattern` 속성 없음 — 이메일 형식 검증은 서버 쪽에서 처리하는 것으로 보임 |
| API | `GET /api/auth/email/check?email={입력값}` |

**에러 처리 (확인됨)**

| 케이스 | 표시 | 비고 |
|--------|------|------|
| 이메일 확인 API 호출 | "이메일 확인에 실패했습니다. 다시 시도해주세요." | **현재 이 API가 503(서비스를 사용할 수 없음)을 반환하고 있어, 유효한 이메일(example.com, gmail.com 도메인 둘 다 테스트)을 넣어도 이 에러가 뜨며 다음 단계로 진행되지 않는다.** 입력값 문제가 아니라 백엔드 쪽 문제로 보인다 |

**2단계 — 닉네임 입력 (프런트 소스 확인됨, `SignupNickname.tsx`)**

| 항목 | 내용 |
|------|------|
| 화면 문구 | "닉네임 설정" / "사용할 닉네임을 알려주세요." |
| 입력 필드 | text, 이메일이 상단에 칩(chip) 형태로 표시됨(`AuthEmailChip`) |
| 클라이언트 검증 | 빈 값(공백 trim 후)이면 "닉네임을 입력해 주세요." — 글자수 상한 클라이언트 검증은 없음(서버 50자 제약만 적용) |
| 다음 단계 | [확인] 클릭 시 `/signup/password`로 이동, `{email, nickname}`을 state로 전달 |

**3단계 — 비밀번호 설정 (프런트 소스 확인됨, `SignupPassword.tsx`)**

| 항목 | 내용 |
|------|------|
| 화면 문구 | "비밀번호 설정" / "안전한 비밀번호로 계정을 완성해 주세요." |
| 입력 필드 | **비밀번호 + 비밀번호 확인 2개 필드가 실제로 존재한다** — 기존 문서(v6.0)가 "비밀번호 확인 필드는 없다"고 정정했던 것은 **서버 전송 페이로드 기준으로만 맞고, 실제 화면 UI에는 비밀번호 확인 입력창이 있다.** 다만 이 값은 클라이언트 검증에만 쓰이고 `POST /api/auth/signup` 요청 바디에는 포함되지 않는다(`signup(email, password, nickname)` 호출부 확인) |
| 클라이언트 검증 | 비밀번호 8자 미만 시 "비밀번호는 8자 이상이어야 합니다.", 두 값 불일치 시 "비밀번호가 일치하지 않습니다." — 100자 상한 클라이언트 검증은 없음(서버 검증에 위임) |
| 약관 동의 체크박스 | "Genstudio의 이용약관과 개인정보 활용에 동의합니다" — 체크 전엔 [확인] 버튼 비활성화 |
| 가입 완료 처리 | `POST /api/auth/signup` 성공 → 곧바로 `GET /api/me/profile` 호출 → 인증 상태로 전환 → **`/home`으로 즉시 이동** — 로그인 화면을 거치지 않는다(프런트 소스 확인됨, `SignupPassword.tsx`의 `handleSubmit`) |
| 이메일 중복(409) 처리 | 가입 요청이 409로 실패하면 `/signup`(1단계)으로 돌아가 "이미 가입된 이메일입니다." 에러를 이메일 입력창에 표시 |

**실제 요청 필드 — API 페이로드 (백엔드 소스 확인됨, `SignUpRequestDto.java`)**

| 필드 | 필수 | 제약 |
|------|------|------|
| 이메일 | ✅ | `@Email` 형식, 최대 **100자** (기존 문서 254자는 오기) |
| 비밀번호 | ✅ | **8자 이상 100자 이하** (기존 문서 "8~64자"는 오기) |
| 닉네임 | ✅ | 최대 50자 — 비밀번호 확인 필드는 서버로 전송되지 않음(위 3단계 설명 참고) |

가입 성공 시 서버가 `provider=LOCAL`, `role=USER`로 계정을 만들고 BCrypt로 비밀번호를 해시해 저장한 뒤(`AuthService.signUp()`), JWT access/refresh 토큰을 발급한다(백엔드 소스 확인됨). **가입 직후 프런트가 `fetchMe()`로 프로필을 받아와 즉시 인증 상태(`setAuthenticated`)로 전환하고 홈 화면으로 보낸다(프런트 소스 확인됨)** — 로그인 화면으로 보내고 토큰을 버리는 것이 아니라 실제로 자동 로그인된다.

**시스템 동작 (프런트+백엔드 소스 확인됨)**
1. 1단계(이메일) → 2단계(닉네임) → 3단계(비밀번호+비밀번호 확인+약관 동의)를 각각 클라이언트 검증 통과해야 다음 단계로 진행
2. 3단계에서 [확인] 클릭 시 `POST /api/auth/signup` 호출 — 요청 중 버튼 텍스트가 "가입 처리 중..."으로 바뀌고 비활성화됨(프런트 소스 확인됨)
3. 서버에서 이메일 중복 확인 → 중복 시 `AUTH_003`(`DUPLICATE_EMAIL`) 409 → 1단계로 리다이렉트 후 에러 표시
4. 계정 생성 완료 → `GET /api/me/profile` 호출 → 인증 상태 전환 → `/home` 이동
5. 그 외 실패 시 3단계 화면에 인라인 에러 메시지 표시

**에러 처리 (백엔드 소스 확인됨 — 3.2절 실제 에러 코드 표 기준)**

| 케이스 | 코드 | 표시 메시지 |
|--------|------|------|
| 이메일 형식 오류·글자수 초과 | `COMMON_001` | "잘못된 입력값입니다." (필드별 상세 메시지는 DTO validation message로 별도 존재, 프런트 노출 방식 재확인 필요) |
| 비밀번호 8자 미만/100자 초과 | `COMMON_001` | "잘못된 입력값입니다." |
| 닉네임 미입력/50자 초과 | `COMMON_001` | "잘못된 입력값입니다." |
| 중복 이메일 | `AUTH_003` | "이미 사용 중인 이메일입니다." |
| 서버 오류 | `COMMON_999` | "서버 내부 오류가 발생했습니다." |

**인수 조건 (프런트+백엔드 소스 확인됨 기준으로 갱신)**
- [ ] 유효한 이메일(100자 이하)·닉네임(50자 이하)·비밀번호(8~100자, 확인값 일치) 입력 시 계정이 생성된다 (필드 자체는 소스 확인됨, 실제 통과 실행은 503으로 재확인 필요)
- [x] 가입 완료 후 **홈 화면**으로 자동 이동한다 — 로그인 화면 아님 (프런트 소스 확인됨)
- [x] 중복 이메일로 가입 시도 시 1단계로 돌아가 에러가 표시되고 계정이 생성되지 않는다 (프런트 소스 확인됨)
- [x] 3단계에서 약관 동의 체크 전에는 [확인] 버튼이 비활성화된다 (프런트 소스 확인됨)
- [ ] 요청 중 연타해도 요청이 1회만 발생한다 (재확인 필요)

**엣지 케이스 (설계 당시 사양, 재확인 필요)**
- 이미 로그인된 상태에서 회원가입 화면 접근 → 홈 화면으로 리다이렉트
- 비밀번호에 공백만 8자 입력 시 그대로 허용되는지는 백엔드 `@Size` 검증만으로는 알 수 없음(문자 수만 검사, 공백 트리밍 로직 없음 — 즉 **공백만으로 구성된 비밀번호도 8자 이상이면 통과할 가능성이 높다**, 재확인 필요)

### 5.2 로그인 (AUTH-002)

이메일/비밀번호 로그인과 **"구글 계정으로 시작하기"** 버튼을 함께 제공한다(확인됨). 화면 배경에 랜덤하게 바뀌는 인물 사진과 "다시 오신 걸 환영해요" 카피가 있다(확인됨).

**UI 구성 요소 (설계 당시 사양)**

| 요소 | 사양 |
|------|------|
| 이메일 입력 | text 필드 |
| 비밀번호 입력 | password 필드, 표시/숨김 토글 |
| [로그인] 버튼 | 두 필드 모두 입력 전 비활성화 |

**시스템 동작**
1. 로그인 API 호출 — 요청 중 버튼 비활성화 + 스피너
2. 인증 성공 → 세션·토큰 발급 → 홈 화면으로 이동 (확인됨)
3. 인증 실패 → 폼 상단 인라인 에러

**에러 처리 (3.2절 실제 에러 코드 표 기준으로 정정)**

| 케이스 | 코드 | 표시 |
|--------|------|------|
| 이메일·비밀번호 불일치 | `AUTH_004`(`INVALID_CREDENTIALS`) | "이메일 또는 비밀번호가 올바르지 않습니다." (백엔드 소스 확인됨 — `AuthService.login()`이 `provider==LOCAL` && 비밀번호 존재 && BCrypt 일치 조건을 하나로 묶어 검사하므로, 미가입/오타/Google전용계정 모두 이 코드 하나로 응답한다) |

- [ ] 실패 메시지는 미가입·비밀번호 오류를 구분하지 않는다 (설계 당시 사양, 재확인 필요)
- [x] 로그인 상태에서 새로고침해도 세션이 유지된다 (확인됨)
- [ ] 세션 만료 후 API 호출 시 3.7절 공통 처리가 동작한다 (재확인 필요)

### 5.3 Google 로그인 (AUTH-002B)

**시스템 동작**
1. "구글 계정으로 시작하기" 버튼 클릭 → Google 동의 화면(`accounts.google.com/o/oauth2/v2/auth`)으로 이동 (확인됨 — 콜백 주소는 `kx-studio.duckdns.org/login/oauth2/code/google`)
2. 인증 성공 → 콜백으로 받은 `sub`(providerId)로 기존 Google 계정 조회 (백엔드 소스 확인됨, `GoogleOAuth2UserService.findOrCreateUser()`)
3. `provider=GOOGLE`이고 `providerId`가 같은 계정이 이미 있으면 그 계정으로 바로 로그인 (백엔드 소스 확인됨)
4. 없으면 이메일 기준으로 **로컬(LOCAL) 계정 존재 여부를 다시 확인** — 이미 그 이메일로 일반 가입된 계정이 있으면 **자동 연동하지 않고 즉시 에러를 던진다** (백엔드 소스 확인됨, 아래 에러 처리 참고)
5. 로컬 계정도 없으면 신규 `User`를 `provider=GOOGLE`, `role=USER`로 생성 후 바로 로그인 처리 (백엔드 소스 확인됨)

**신규 계정 닉네임 결정 규칙 (백엔드 소스 확인됨)**: Google 프로필의 `name` 값이 있으면 그대로 닉네임으로 쓰고, 없으면 이메일의 `@` 앞부분을 닉네임으로 사용한다.

**계정 속성 (Google 로그인 사용자)**
- 비밀번호 없음(User 엔티티의 `password` 컬럼이 nullable, 백엔드 소스 확인됨) → 로그인 시 `provider==LOCAL` && 비밀번호 존재 조건으로만 비밀번호 매칭을 시도하므로, Google 계정으로는 애초에 이메일/비밀번호 로그인이 불가능한 구조다(백엔드 소스 확인됨)
- 실제 프로필 화면(11장)에는 로그인 방식과 무관하게 비밀번호 변경 항목 자체가 없음(확인됨)
- Google 계정 연결 해제 기능은 프런트·백엔드 어디에도 확인되지 않음

**에러 처리 (백엔드 소스 확인됨)**

| 케이스 | 코드 | 표시 메시지 |
|--------|------|------|
| OAuth 인증 실패·취소, 필수 속성(sub/email) 누락 | `AUTH_006`(`INVALID_OAUTH2_USER`) | "OAuth 사용자 정보를 확인할 수 없습니다." |
| **이메일 계정과 충돌** — 이미 일반 회원가입된 이메일로 Google 로그인 시도 | `AUTH_005`(`OAUTH_EMAIL_ALREADY_EXISTS`) | "이미 일반 회원가입으로 가입된 이메일입니다." — **자동 연동되지 않고 409로 거부된다.** (기존 "확인되지 않은 사항"이었던 항목이 이번 소스 확인으로 해소됨) |

**인수 조건**
- [ ] "구글 계정으로 시작하기" 클릭 시 최초 사용자는 별도 회원가입 절차 없이 계정이 생성되고 로그인된다 (백엔드 로직상 성립 — 프런트 화면 재확인 필요)
- [x] Google 로그인 사용자의 내 프로필 화면에는 비밀번호 변경 항목이 노출되지 않는다 (확인됨)
- [ ] 이미 일반 가입된 이메일로 Google 로그인 시도 시 에러 메시지가 프런트에 표시된다 (백엔드는 409를 반환함이 확인됨 — 프런트가 이를 사용자에게 어떻게 보여주는지는 재확인 필요)

## 7. 이미지 생성

모델은 **GPT Image 2.0으로 고정**되어 있다(확인됨). 상단 "유형" 탭으로 세 가지 생성 방식을 선택한다.

### 7.1 유형 — 캐릭터 / 배경 / 캐릭터시트 (M001, 확인됨 + 프런트·백엔드 소스 확인됨)

**"캐릭터시트"는 `purpose=CHARACTER`+`multiViewEnabled` 조합이 아니라, 완전히 별도인 전용 엔드포인트로 구현돼 있다.** 프런트 소스(`src/services/imageGeneration.ts`)를 확인한 결과, 화면의 "유형" 탭 3개는 실제로 API 레벨에서도 3갈래로 나뉜다.

| 유형(화면 기준) | 실제 엔드포인트 | 각도 옵션 | 결과물 |
|------|------|---------|--------|
| 캐릭터 | `POST /api/generate/images` (`purpose=CHARACTER`) | 단일 / 다각도(`multiViewEnabled`, null이면 true로 처리됨 — 프런트 주석 확인됨) | 단일: 캐릭터 이미지 1장 · 다각도: 정면·측면·후면 세트로 추정(재확인 필요) |
| 배경 | `POST /api/generate/images` (`purpose=BACKGROUND`) | 없음(`multiViewEnabled` 값 자체를 요청에 안 실음) | 배경 이미지 1장 |
| 캐릭터시트 | **`POST /api/generate/images/character-concept-sheet` — 완전히 다른 엔드포인트, `purpose` 필드 자체가 없음** | 해당 없음 | 턴어라운드+표정+소품+컬러 팔레트 포함 캐릭터 시트로 추정(재확인 필요) |

**캐릭터시트 상세 입력 방식 — "확인되지 않은 사항"이었던 항목이 이번 프런트 소스 확인으로 해소됨:** 설계 당시 문서가 언급했던 "자유 텍스트 입력 vs 속성 선택 사이드바" 중, 실제 구현은 **속성 선택 사이드바 방식**이다. `characterConceptSheet()` 요청 바디가 구조화된 필드로 구성돼 있다(프런트 소스 확인됨):

| 요청 필드 | 대응하는 옛 설계상 파트 |
|------|------|
| `gender`, `age`(ageGroup), `bodyType` | 파트1 캐릭터 기본 |
| `artStyle`(style), `worldView`(worldSetting) | 파트2 아트 스타일·세계관 |
| `hairLength`, `hairStyle`, `hairColor` | 파트3 헤어 |
| `expression`, `eyeColor`, `eyeCharacteristic` | 파트4 얼굴 |
| `outfitGenre`, `outfitColor`, `accessories`(배열) | 파트5 의상·악세서리 |
| `additionalPrompt` | 구조화 필드 외 자유 서술 추가 입력 — 옛 "PART1 자유 텍스트" 흔적이 이 필드로 남은 것으로 추정 |

즉 실제로는 "자유 텍스트 vs 속성 사이드바" 양자택일이 아니라, **속성 사이드바가 메인이고 `additionalPrompt` 자유 입력칸이 보조로 붙어 있는 구조**다. 컬러 팔레트/헥스코드 직접 입력 UI가 그대로인지, 요청 시 `imageCount`/`size`/`quality`도 함께 전송되는지(요청 바디에 확인됨)는 프런트 소스로 필드 존재는 확인했으나 실제 UI 노출 형태는 재확인 필요.

### 7.2 공통 옵션 (확인됨 + 백엔드 소스 확인됨)

| 옵션 | 값 | 출처 |
|------|-----|------|
| 비율(`size`) | `auto` · `1024x1024` · `1536x864` · `864x1536` (정규식으로 이 4개 값만 허용, 백엔드 소스 확인됨) | 백엔드 소스 확인됨 — 화면상 "1:1/16:9/9:16" 라벨이 이 픽셀 값에 매핑되는 것으로 추정 |
| 품질(`quality`) | `standard` · `high` 2단계만 존재 (기존 문서의 "4K"는 실제 파라미터명이 아니며, 화면에 "4K"로 표시되더라도 서버로는 `high`로 전송될 가능성이 높음) | 백엔드 소스 확인됨 |
| 수량(`imageCount`) | 1~4장 (`@Min(1) @Max(4)`) | 백엔드 소스 확인됨 |
| 레퍼런스 이미지 | 최대 8장 첨부 가능 (설계 문서엔 없던 기능, 화면상 확인됨. 이 DTO 자체엔 레퍼런스 이미지 필드가 없어 별도 엔드포인트/파라미터로 처리되는 것으로 추정, 재확인 필요) | 확인됨 |
| AI 프롬프트 변환(`promptCorrectionEnabled`) | boolean, 기본값 Off로 추정. On 시 입력한 한국어를 백그라운드에서 영어 프롬프트로 변환한 뒤 생성 요청(변환 결과 미리보기는 없음). hover 보조 문구: "입력한 내용을 이미지 생성용 영어 프롬프트로 다듬어드려요" | 확인됨(동작) + 백엔드 소스 확인됨(필드명) |
| 프롬프트 입력창 | textarea, 자동 높이 확장. **1자 이상, 최대 2,000자** (`@NotBlank`, `@Size(max=2000)` — 백엔드 소스 확인됨. 기존 문서의 "GPT Image 2 API 자체 한도 32,000자" 서술은 백엔드 검증 제약과 무관하므로 삭제) | 백엔드 소스 확인됨 |

### 7.3 이미지 생성 호출 (M002)

**시스템 동작 (설계 당시 사양, 흐름 자체는 확인됨)**

3. 생성 요청 — 버튼 비활성화 + 결과 영역 Loading (확인됨)
4. 클라이언트 타임아웃 60초로 설계됨
5. 성공 → 결과 영역에 이미지 표시 (확인됨)

**에러 처리 (3.2절 실제 에러 코드 표 기준으로 정정)**

| 케이스 | 코드 | UI 동작 |
|--------|------|--------|

**인수 조건**
- [x] 캐릭터/배경/캐릭터시트 유형에서 프롬프트 입력 후 [생성] 클릭 시 이미지가 생성된다 (확인됨)
- [x] AI 프롬프트 변환 토글 On 상태에서 생성 시 영어 프롬프트 미리보기 없이 바로 생성이 진행된다 (확인됨)

- [x] 선택한 비율이 생성 결과에 반영된다 (확인됨)
- [ ] 빈 프롬프트로는 생성 요청이 발생하지 않는다 (재확인 필요)
- [ ] 실패 시 에러 메시지와 [다시 시도] 버튼이 표시된다 (재확인 필요)

### 7.4 생성 결과 표시·자동 저장 (M003, M004)

생성이 끝나면 결과 영역에 이미지가 원본 비율로 표시되고, 라이브러리에도 즉시 자동 저장된다(확인됨). 결과를 클릭하면 라이브러리 상세보기와 동일한 **우측 패널**이 열리며, 아래 버튼을 제공한다(확인됨).

- [재편집]
- [동영상 만들기] — 이 이미지를 가지고 영상 생성 화면으로 이동(이미지가 프리필되는 것으로 추정)
- [다운로드] — PNG 원본, 파일명 규칙은 3.8절 참고
- [삭제]

**재생성**: [재생성]을 누르면 기존 프롬프트·옵션이 유지된 채로 다시 생성을 요청한다(확인됨). 새 결과는 별도의 라이브러리 항목으로 저장되며, 기존 결과는 삭제되지 않는다.

## 8. 영상 생성

모델을 **Seedance 2.0 / Kling 3.0** 중에서 고르며, 어떤 모델을 선택하느냐에 따라 아래 옵션 전체가 달라진다(확인됨).

### 8.1 모델별 옵션 (확인됨)

**Seedance 2.0**

| 옵션 | 값 |
|------|-----|
| 길이 | 4초 · 5초(기본) · 8초 · 10초 · 15초 · 자동 |
| 비율 | 16:9·1376×768(기본) · 9:16·768×1376 · 1:1·1024×1024 · 21:9 · 4:3 · 3:4 · 자동 |
| 품질 | 고화질 1920×1080(기본) · 표준 1280×720 · 480p · 4K |
| 레퍼런스 이미지 | 최대 9장 |

**Kling 3.0**

| 옵션 | 값 |
|------|-----|
| 길이 | 3초 · 4초 · 5초(기본) · 8초 · 10초 · 15초 |
| 비율 | 16:9·1376×768(기본) · 9:16·768×1376 · 1:1·1024×1024 |
| 품질 | 별도 선택 옵션 없음 |
| 레퍼런스 이미지 | 최대 4장 |

두 모델 다 실사용 가능한 정식 옵션이며, 어느 한쪽이 "테스트 전용"으로 제한되어 있지는 않다.

**Kling 3.0 품질 옵션 부재 — 프런트 소스 확인으로 최종 확정.** 영상 생성 요청 DTO(`ImageToVideoGenerateRequestDto`)는 `modelId`+`options: Map<String, Object>` 자유 형식이라 백엔드 제약이 아니라는 점은 이미 확인했었고, 이번에 프런트 소스(`src/utils/videoOptionMapping.ts`)까지 확인한 결과 **의도적으로 막아둔 프런트 설정임이 확정됐다.** `MODEL_CAPABILITIES` 객체에서 Kling 항목은 `qualityOptions: []`(빈 배열)로 하드코딩되어 있고, Seedance 항목만 `qualityOptions: ['고화질 1920×1080', '표준 1280×720', '480p', '4K']`를 갖는다. `generateVideo()`는 `capability.qualityOptions.length > 0`일 때만 `resolution` 옵션을 요청에 실어 보낸다. 즉 **"원인 불명(회귀 추정)"이 아니라 프런트가 Kling에 대해 품질 옵션 UI 자체를 의도적으로 숨긴 것**이며, 버그나 누락이 아니다.

### 8.2 입력 (A002)

- **스토리보드 이미지** (필수, 1장) — 미리 준비한 스토리보드 이미지를 업로드한다. 설계 당시엔 "3x3 그리드 이미지 업로드"라는 이름으로, Kling 3.0 I2V 모델 특성상 그리드 이미지가 첫 프레임으로 그대로 사용돼 노출·순서 오류가 나는 문제가 보고된 적 있다. 지금은 "스토리보드" 업로드로 이름과 UI가 바뀌었고, 이번 검증 범위(업로드 자체)에서는 문제가 재현되지 않았다.
- **레퍼런스 이미지** (선택) — 스토리보드와 별개 슬롯. 최대 개수는 모델에 따라 다름(8.1절 참고)
- 프롬프트 입력창 — 설계 당시 제약: 1자 이상, 최대 2,000자

**오디오 (확정 — 담당 PM 확인)**: **영상은 무조건 오디오가 포함되도록 생성되며, 켜고 끄는 토글은 없다.** 프런트 소스에서도 영상 생성 요청 시 `options.generate_audio: true`가 항상 하드코딩되어 전송되는 것으로 확인된다(`videoGeneration.ts`의 `generateVideo()`). UI에 오디오 토글이 없는 것은 미구현이 아니라 의도된 사양이다.

**입력 필드 제약**

| 필드 | 필수 | 비고 |
|------|------|------|
| 프롬프트 | ✅ | 1자 이상, 최대 2,000자로 설계됨(재확인 필요 — `ImageToVideoGenerateRequestDto.prompt`엔 별도 길이 제약 어노테이션이 없음, 백엔드 소스 확인됨) |
| 스토리보드 이미지 | ✅ | 업로드는 공용 이미지 업로드 API(`/api/media/images/upload`)를 거치며, **PNG·JPG·WEBP 형식에 50MB 이하**가 실제 제약이다(기존 문서 "jpg·png, 10MB 이하"는 오기 — 백엔드 소스 확인됨, `UploadedImageFileValidator`) |
| 모델 | ✅ | 기본값 설계 당시 kling-3 → 실제는 seedance 2.0 기본 노출(확인됨, 정정) |

백엔드 DTO 기준으로는 `startMediaFileId`/`endMediaFileId`(시작·끝 프레임 이미지), `referenceMediaFileIds`(최대 9장), `modelId`, `prompt`, `options`(모델별 자유 파라미터)로 구성된다(백엔드 소스 확인됨). 화면의 "스토리보드 이미지"가 `startMediaFileId`에 매핑되는 것으로 추정되나 정확한 대응은 프런트 소스 확인이 필요하다(재확인 필요).

**에러 처리 (3.2절 실제 에러 코드 표 기준으로 정정)**

| 케이스 | 코드 | UI 동작 |
|--------|------|--------|
| 프롬프트 빈값 | — | 버튼 비활성화 |

## 9. 역프롬프트

레퍼런스 이미지를 분석해 그 이미지를 재현할 수 있는 프롬프트를 추출하는 기능이다.

| 항목 | 내용 |
|------|------|
| 분석 모델 | Claude Sonnet 5 (멀티모달, 확인됨) |
| 비율(`aspectRatio`) | `auto`(기본) · `1:1` · `16:9` · `9:16` — 정규식으로 이 4개 값만 허용 (확인됨 + 백엔드 소스 확인됨, `ReversePromptRequestDto`) |
| 업로드 | 이미지 1장. **실제 파일 제약: PNG·JPG·WEBP, 50MB 이하** (기존 문서 "10MB 이하"는 오기 — 공용 이미지 업로드 API의 검증 로직으로 확인됨, `UploadedImageFileValidator.MAX_IMAGE_FILE_SIZE_BYTES = 50MB`) |

역프롬프트 요청 자체(`ReversePromptRequestDto`)는 `mediaFileId`(사전 업로드된 이미지 참조)와 `aspectRatio`만 받는다(백엔드 소스 확인됨) — 즉 이미지는 먼저 `/api/media/images/upload`로 업로드해 ID를 받은 뒤, 그 ID로 분석을 요청하는 2단계 구조로 추정된다(재확인 필요).

### 9.1 이미지 업로드 (S001)

**UI 구성 요소 (설계 당시 사양, 파일 제약 수치는 백엔드 소스 확인됨으로 정정)**

| 요소 | 사양 |
|------|------|
| 업로드 영역 | 드래그앤드롭 + 클릭 파일 선택 겸용 |
| 파일 제약 안내 | "png, jpg, webp · 50MB 이하"로 노출되어야 함(기존 "10MB 이하" 문구는 실제와 다름) |
| [프롬프트 생성] 버튼 | 유효한 파일 업로드 전 비활성화 |

**에러 처리 (백엔드 소스 확인됨 — 실제로는 형식 오류·용량 초과 모두 동일 코드, 메시지만 다름)**

| 50MB 초과 | `COMMON_001`(`INVALID_INPUT_VALUE`) | "{대상}는 50MB 이하만 업로드할 수 있습니다." — 기존 `FILE_TOO_LARGE` 코드·"10MB" 수치 모두 오기 |

### 9.2 이미지 분석·프롬프트 추출 (S002)

**에러 처리 (3.2절 실제 에러 코드 표 기준으로 정정)**

| 케이스 | 코드 | UI 동작 |

| 분석 실패(Claude 호출 실패) | `GENERATE_001` | "이미지 분석에 실패했습니다. 다시 시도해주세요" + [다시 시도] — 기존 `ANALYSIS_FAILED`/`TIMEOUT`은 실제로 없고 이 코드로 통합됨 |

**인수 조건**
- [ ] ~~업로드한 이미지에서 스타일·조명·구도·렌즈·색감·분위기 6개 항목이 추출된다~~ — **실행 확인됨: 해당 사항 없음.** 태그 UI 자체가 존재하지 않아 이 인수 조건은 폐기한다
- [ ] 추출된 영문 프롬프트가 80단어 이하로 표시된다 (실행 결과 프롬프트가 80단어를 넘는 경우도 관찰됨 — 정확한 단어 수 제한 로직 재확인 필요)
- [x] [복사] 클릭 시 프롬프트가 클립보드에 복사된다 (확인됨)

### 9.3 결과 화면 — 수정·재생성 연결 (S003, S004)

**결과 화면 구조가 설계 문서와 다르다(확인됨) — 중요**

- 결과에는 **[복사] 아이콘**과 **더보기(⋮) 아이콘**, 두 개만 우선 노출된다. 설계 문서처럼 프롬프트 에디터가 바로 펼쳐져 있는 게 아니라, 더보기 아이콘을 눌러야 **[수정]** / **[이 프롬프트로 이미지 생성]** 두 버튼이 나오는 구조다.
- **[수정]** — 누르면 프롬프트 텍스트뿐 아니라 **비율도 함께 수정 가능** (설계 문서는 프롬프트 텍스트만 언급, 비율 수정은 없었음)
- **[이 프롬프트로 이미지 생성]** — 해당 프롬프트로 바로 이미지 생성 실행 (설계 당시 버튼명 "[이 프롬프트로 이미지 생성]"과 동일 기능으로 보임)
- **역프롬프트로 추출된 프롬프트 자체는 라이브러리에 저장되지 않는다.** 설계 문서는 "생성과 동시에 자동 저장"이라 했는데, 실제로는 **[이 프롬프트로 이미지 생성]를 눌러 이미지가 실제로 생성된 시점에만** 그 결과 이미지가 라이브러리에 저장되는 것으로 보인다.

**에러 처리 (3.2절 실제 에러 코드 표 기준으로 정정)**

| 케이스 | 코드 | UI 동작 |
|--------|------|--------|
| 생성 실패 | `GENERATE_001` | 결과 영역 에러 상태 + [다시 시도] |

**인수 조건**
- [x] [이 프롬프트로 이미지 생성] 클릭 시 화면 전환 없이 같은 페이지에서 이미지가 생성되는 것으로 추정 (재확인 필요 — 실제 실행은 안 해봄)
- [ ] 생성이 완료되면 별도 조작 없이 라이브러리에 자동 반영된다 (재확인 필요)
- [ ] 업로드 → 추출 → 수정 → 재생성까지 5분 이내에 완료 가능하다 (설계 당시 목표치, 재확인 필요)

**엣지 케이스 (설계 당시 사양)**

### 10.1 상세보기

**기존 문서(v6.0 이하)의 "이미지=우측 고정 패널, 영상=풀스크린 모달" 구분은 틀렸다.** 사용자 스크린샷과 프런트 소스(`MediaDetailPanel.tsx`) 확인 결과, **이미지·영상 모두 동일한 컴포넌트(`MediaDetailPanel`)가 같은 오버레이 구조로 열린다** — 미디어(이미지/영상)가 왼쪽 큰 영역에, 우측에 360px 고정폭 정보 패널이 붙는 하나의 모달형 오버레이다. 차이는 내부 콘텐츠와 하단 버튼 구성뿐이다.

**공통 구조 (프런트 소스 확인됨)**
- 우측 패널 상단: 작성자 아바타 + `@핸들` (예: `@my_studio`), **찜하기(하트) 버튼은 이미지·영상 모두 동일하게 존재한다** — "이미지 패널에도 하트가 있는지" 열려 있던 질문 해소(사용자 확인 + 소스 확인 일치)
- 좌측 미디어 영역 우상단에 공유(Share2) 아이콘 — 이미지·영상 공통
- 프롬프트 텍스트(복사 버튼 포함, 3줄 초과 시 "전체 보기"로 펼침) + 모델/품질/비율/(영상만) 길이/생성일자/작업 ID 메타 정보 표
- 하단 액션 버튼: **[재편집]은 공통.** **[영상 만들기]는 이미지일 때만 노출**(`art.type === 'image'`). **[다운로드]는 공통**이나 영상은 URL이 아직 없으면 비활성화

**이미지·영상 버튼 차이**
| 타입 | 하단 버튼 |
|------|------|
| 이미지 | [재편집] · [영상 만들기] · [다운로드] |
| 영상 | [재편집] · [다운로드] (영상 만들기 버튼 없음, 당연히) |

**[삭제] 버튼은 이 상세보기 패널 안에 없다.** 기존 문서가 이미지 상세보기에 [삭제]가 있다고 적었던 것은 오류다 — 실제로는 **삭제·다운로드·찜·더보기(재편집/재생성/동영상 전환) 메뉴가 라이브러리 그리드의 각 카드에 마우스를 올렸을 때(hover) 나타나는 액션바에 있으며, 이미지·영상 카드 모두 동일한 구성**이다(프런트 소스 확인됨, `ResultCard.tsx`).

이미지·영상 생성 화면에서 방금 만든 결과를 클릭했을 때도 이 `MediaDetailPanel`과 동일한 UI가 뜬다(확인됨).

**다운로드 API (확인됨)**: `GET /api/media/images/{id}/download`

### 10.2 삭제 (그리드 카드 hover 액션, 프런트 소스 확인됨 · `ResultCard.tsx`)

**[삭제]는 상세보기 패널이 아니라 라이브러리 그리드의 각 카드에 마우스를 올렸을 때 나타나는 액션바(하트·다운로드·삭제·더보기)에 있다.** 실제 삭제 API는 `DELETE /api/media/files/{mediaFileId}`(프런트 소스 확인됨). 확인 모달 유무 등 클릭 이후 흐름은 이번 검증에서 실제 삭제를 실행하지 않아 재확인이 필요하다.

**에러 처리 (3.2절 실제 에러 코드 표 기준으로 정정)**

| 케이스 | 코드 | HTTP |

| 존재하지 않거나 이미 삭제된 항목 | `COMMON_004`(`NOT_FOUND`) | 404 |

- [ ] 삭제는 확인 모달을 거쳐야만 실행된다 (재확인 필요 — 이번 검증에서 실제 삭제는 실행하지 않음)

### 10.3 찜하기 (프런트 소스 확인됨)

하트 아이콘은 **라이브러리 그리드 카드(hover 액션바)와 상세보기 패널(`MediaDetailPanel`) 양쪽 모두에 있으며, 이미지·영상 타입 구분 없이 동일하게 노출된다.** API는 토글용 PATCH 하나가 아니라 `POST /api/media/files/{id}/favorite`(추가)·`DELETE /api/media/files/{id}/favorite`(해제) 두 엔드포인트로 분리돼 있다(프런트 소스 확인됨).

## 11. 내 프로필

사이드바 하단 프로필 영역을 클릭하면 진입한다(확인됨: `GET /api/me/profile`). 세 개의 카드로 구성된다.

### 프로필 카드 (AUTH-003)
- 프로필 이미지 (원형, [이미지 변경] 버튼)
- 스튜디오 이름 (텍스트 입력 + [저장])
- 이메일 (표시만, 수정 불가)

설계 당시엔 이 필드가 "닉네임"이었고, 로그인 방식 뱃지("일반"/"Google")와 가입일도 함께 표시하도록 되어 있었다. 실제 화면에는 "스튜디오 이름"이라는 이름으로 바뀌어 있고, 로그인 방식 뱃지와 가입일은 없다. **"스튜디오 이름" 필드는 백엔드 `User.nickname` 컬럼과 동일한 값이며(회원가입 3단계 마법사에서 입력받는 그 닉네임, `AuthProfile.nickname`), 별도 저장 필드가 아니다 — 담당 PM 확인.**

**`@핸들`(라이브러리·상세보기에 노출되는 `@my_studio` 형태)과 "스튜디오 이름"의 관계 — 프런트 소스 확인으로 최종 확정.** `src/constants/mockData.ts`에 `ME` 상수가 `{ id: 'me', handle: '@my_studio', avatar: ... }`로 **하드코딩**되어 있다. 즉 `@my_studio`는 로그인 계정의 실제 닉네임(`nickname`)과 전혀 연동되지 않은 고정 목업 값이며, 어떤 계정으로 로그인해도 동일하게 `@my_studio`로 표시된다 — 담당 PM이 "별도 생성 로직 없이 정해진 값"이라 했던 것과 정확히 일치한다. 실제 서비스 오픈 전 이 부분을 로그인 사용자의 진짜 닉네임과 연동하는 작업이 필요하다.

### 로그인 & 보안 (AUTH-004, 설계 당시 사양)

설계 문서는 일반 가입자에게 비밀번호 변경(현재 비밀번호/새 비밀번호/새 비밀번호 확인, 8자 이상 64자 이하)을, Google 로그인 사용자에게는 계정 연결 상태(해제 불가)를 보여주도록 계획했다. **실제 화면에는 이 섹션 자체가 없다(확인됨).**

### 활동 카드
- "내 생성 이력" 안내 문구 + [라이브러리로 이동] 버튼
- 별도의 통계·수치 표시는 없다 (설계 당시에도 크레딧/사용량 표시는 범위 제외로 명시되어 있었음)

### 위험 구역 (Account Deletion) — 회원 탈퇴 (AUTH-006)
- 회원 탈퇴 안내 문구 + [계정 삭제] 버튼
- 클릭 시 **브라우저 기본 확인창**(취소/확인)이 뜨며, 확인하면 계정과 라이브러리의 모든 생성물이 즉시 영구 삭제된다(확인됨)

**설계 당시 사양과의 차이**: 설계 문서는 이 확인 단계를 "계정이 영구적으로 삭제됩니다" 안내와 삭제 항목 체크리스트(모든 생성물 접근 권한 / 라이브러리 저장 콘텐츠 / 저장된 설정), "이해했습니다" 체크박스를 체크해야 [계정 삭제하기] 버튼이 활성화되는 커스텀 모달로 계획했다. 실제로는 그런 커스텀 디자인 없이 브라우저 기본 확인창으로 구현되어 있다 — 애초에 커스텀 디자인이 적용된 적 없는 상태로, 그 자체가 문제는 아니다.

**시스템 동작 (설계 당시 사양)**
1. [회원 탈퇴] 클릭 → 확인창 노출
2. 확인 → 계정 및 라이브러리 생성물 즉시 삭제
3. 탈퇴 완료 → 세션 종료 → 로그인 화면 이동 + 완료 토스트

**인수 조건 (설계 당시 사양)**
- [ ] 확인창에서 취소하면 탈퇴가 진행되지 않는다
- [ ] 확인하면 계정과 라이브러리 생성물이 즉시 삭제된다
- [ ] 탈퇴 완료 후 로그인 화면으로 이동한다

**이번 범위에서 제외된 것으로 확인된 항목 (설계 당시에도 제외로 명시됨)**
- 크레딧/사용량 표시
- 내 생성 이력/라이브러리 바로가기를 프로필 화면 안에 별도로 두는 것 (사이드 메뉴와 중복)
- 생성 완료 알림 토글, 세션·기기 관리, 언어·테마 설정
